# Security policy

Permaura sits between AI agents and real credentials. A vulnerability here is somebody's
production API key, so we would rather hear about a false alarm than miss a real one.

## Reporting a vulnerability

**Email [security@permaura.com](mailto:security@permaura.com).** Do not open a public issue or
discussion, and do not post it in a pull request description.

Useful to include, as much as you have: what an attacker gains, the steps to reproduce it, the
version or commit you tested, and whether it needs a paired device, an operator token, or network
access to the gateway. A proof of concept helps and is never required.

We will acknowledge your report, tell you what we think it is, and keep you updated until it is
resolved. If we disagree that something is a vulnerability we will say so and explain why, rather
than going quiet.

Please give us a reasonable window to ship a fix before disclosing publicly. We will not threaten
legal action over good-faith research, and we are happy to credit you in the release notes if you
would like to be.

The canonical machine-readable contact is
[permaura.com/.well-known/security.txt](https://permaura.com/.well-known/security.txt). This file is
the disclosure policy; [permaura.com/security](https://permaura.com/security) describes how the
product is built to protect credentials.

## What is in scope

The gateway, the enforcement core, the policy engine, the connectors, the CLI, the relay protocol
and the SDKs in this repository. The hosted service at permaura.com and the desktop and phone apps
are in scope too, even though their source lives elsewhere.

Particularly interesting:

- Anything that resolves a secret to plaintext outside a single approved call, or that returns one
  to an agent.
- Anything that lets an approval be forged, replayed, resolved by the wrong principal, or resolved
  without the signatures the policy demands.
- Anything that lets the control plane, the relay, or a broker-relayed request reach an operation
  that is supposed to be limited to the gateway's own host, or pair a device without the authority
  pairing requires: the gateway's own host on a self-run gateway, or a single-use ticket from a
  fresh re-authentication of the owning account on a hosted one.
- Anything that turns a policy decision from deny into allow without the operator's involvement.

## What is not

Findings that need an attacker who already has root on the gateway host or physical access to an
unlocked paired device, and findings that need the operator token on a gateway with no paired
device. Those are outside the model rather than uninteresting: custody and execution are
inseparable, which [the docs](https://docs.permaura.com) say plainly. Once a device is paired the
operator token is meant to be bounded, so anything that lets it alone export the vault, make a
destructive change or loosen the gateway's trust settings is in scope. Also out of scope: missing
hardening headers with no demonstrated impact, rate limits on unauthenticated endpoints that are
already rate limited, volumetric denial of service, and reports generated by a scanner with no
analysis attached.

## Supported versions

Security fixes go into the latest release of the gateway (the `permaura` binary and the `permaura`
npm launcher), the desktop app and the phone app. Older versions do not get them, so if you are
pinned, please plan to move. `@permaura/gateway` is the launcher's old npm name; it stopped at 1.3.0
and gets no fixes. A hosted gateway is upgraded by a rollout after each release, so it can run one
release behind the latest for a while.
