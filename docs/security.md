# Security architecture

This document describes the mechanisms that implement Permaura's trust boundaries as they ship today: envelope encryption of stored secrets, where the vault key lives on each platform, the tamper-evident audit chain, device-signed approvals and the trust state behind them, the redaction layer, and deny-by-default. It also states the boundaries the design does not cross, because an operator choosing a deployment needs those as much as the guarantees. For the adversary model these mechanisms answer, read [threat-model.md](./threat-model.md) first.

## Envelope encryption

Permaura never encrypts a secret directly with a long-lived key. Each stored secret value is sealed in two layers.

- **DEK (data encryption key).** A fresh random key generated for that secret. The plaintext is encrypted under the DEK with an AEAD cipher.
- **Wrapping key.** Derived from the vault key with Argon2id and a per-secret random salt. It wraps the DEK. The salt and the Argon2id parameters are stored beside the ciphertext as non-secret metadata so the derivation is reproducible.

```text
secret plaintext  --AEAD(DEK)-->         ciphertext
DEK               --AEAD(wrapping key)--> wrapped DEK
wrapping key      = Argon2id(vault key, per-secret salt)
vault key         held outside the database, see custody below
```

The sealed record (ciphertext, wrapped DEK, salt, nonces, cipher id) is what the store holds for a secret. A copy of the database on its own opens no secret, because opening a sealed record needs the vault key, but it does yield everything the store keeps in plain rows, as the next paragraph says.

Two things this is not. The vault key is random material, not a user-chosen passphrase, so there is nothing to brute-force by guessing words; Argon2id is there so that a copied database plus a partially exposed key is still expensive to work through. And the database file is not itself encrypted: secret values are sealed and session tokens and enrolment codes are stored as digests, while policies, grants, agent records, approval trust state, connection metadata, held calls with their full parameters and results, and the audit chain are plain rows protected by file permissions only. An earlier version of this document described a SQLite encryption layer. There is none.

## Ciphers

- **Secret encryption:** AES-256-GCM by default, ChaCha20-Poly1305 where a constant-time software implementation is preferable. Both are AEAD, so tampering with ciphertext is detected on decrypt. Each encryption uses a unique nonce.
- **Key derivation:** Argon2id, memory-hard and side-channel resistant.
- **Signatures:** ed25519 for the audit chain, device approvals, pairing blobs, release manifests and connector envelopes. Every check is strict (`verify_strict`), and a small-order or non-canonically encoded public key is refused wherever one is accepted, so no weak key can be paired or trusted.

## Where the vault key lives

The vault key is generated on first start (or, on macOS, adopted from an entry already standing under the gateway's name, as the table says) and kept by the gateway itself. Which custody it gets is decided at runtime from what the platform and the build can offer, and is reported in the gateway's health document rather than assumed.

| Platform | Custody of the vault key | What that protects against |
|---|---|---|
| macOS, released gateway | The user's default keychain, normally the login Keychain, in an entry bound to the gateway's Developer ID code identity. Once the gateway has written the entry, another program asking for it gets a system dialog, not the key. The gateway adopts an entry already standing under its name, though, so a program running as the same user before the gateway's first start, or before a reset makes it mint a new key, can plant that entry with an access list that admits every application, or repoint the default keychain, and so choose or read the key. | A different process running as the same user reading the key silently, from the gateway's own first write onward. |
| macOS, unsigned or file-configured build | An owner-only (`0600`) file, `vault-kek`, under the Permaura home. | Other users on the machine. |
| Windows | Credential Manager, per user. There is no code-identity check, so a program running as the same user reads it without a prompt. Falls back to an owner-DACL file where the native store is unavailable. | Other users on the machine. |
| Linux | An owner-only file by default. The installer can instead seal the key into a systemd credential under the TPM, which protects a copy of the disk but not a process running as the service user. The shipped static binary does not talk to Secret Service. | Other users, and offline disk copies under the TPM option. |
| Hosted worker | A file mounted from Secret Manager into the container, granted to that tenant's runtime service account alone. Permaura administers the Google Cloud project, and a project owner can grant themselves access, so Permaura can read it. | Other tenants, and anyone outside Permaura without that identity. |

The Secure Enclave is not involved on any platform, and no biometric prompt gates a decrypt. An earlier version of this document claimed both. The Keychain entry protects who may read the key; once the gateway holds it, the gateway decrypts on its own authority.

The same custody layer holds the desktop app's approver signing seed and its account tokens, with the same properties: a software Ed25519 seed in the Keychain or Credential Manager, or an owner-only file. A device-signed approval proves possession of that seed. The Touch ID or Windows Hello prompt the desktop shows is a separate step in front of signing, not a property of the signature, so an approval carries no cryptographic proof that a person was prompted.

## Approval trust state

Which devices may sign approvals, and the approval floor that decides whether a bare operator token may resolve anything, are the trust root of the human-approval gate. Both persist in the gateway's own store (`gateway_meta`), on every placement, so a restart or a redeploy comes back trusting exactly the devices it trusted before. An install that sets `PERMAURA_APPROVER_KEYS_PATH` keeps that file instead, written atomically, and a file that exists but cannot be read refuses to start rather than loading as an empty keyring. An empty keyring is not a neutral state: it switches off the device holds on vault exports, destructive changes and credential moves, so anything that could produce one silently would be a fail-open.

Pairing a device does not raise the floor. It defaults to `approve`, at which an operator token can resolve any held call whose policy rung is `approve`; High and Critical risk raise a rung only as far as `approve`, and a rung set to `device_signed` refuses a bearer whatever the floor. Raising the floor to `device_signed` for every approval is offered when the first device is paired and can be set at any time (`PUT /v1/approval-floor`, or `PERMAURA_REQUIRE_DEVICE_SIGNED_APPROVAL=1`), and a gateway that already had a device paired when it upgraded to 1.3.17 kept the device-signed floor it had. Once a device is trusted, the two controls that could switch the device hold off (lowering the floor, revoking the last trusted key) need a device signature, a single-use recovery code issued at first pairing, or, where the gateway has remote access configured, a single-use recovery ticket from permaura.com. A gateway with no authorization server has no third route. A local reset (`permaura approver reset --yes --recovery-code` on its host, with the gateway stopped; the flag on its own asks for the code with the input hidden, and `PERMAURA_RECOVERY_CODE` also works) untrusts every device and reopens bearer-only approvals, and while a device is trusted it is possible only with a recovery code, because anything running as the owner can stop the gateway too. With neither the device nor a code, no reset keeps the vault: `permaura uninstall --purge-data` starts the gateway over and destroys every credential it held.

An explicit opt-down to `approve` is not the same state as the untouched default, though both resolve to the effective floor `approve`: only the opt-down switches off the device holds on remote control-plane changes, vault exports and destructive mutations. `GET /v1/devices` and the floor's own responses therefore report `approval_floor_override` (`approve`, `device_signed` or null) and `approvals_opted_down` beside the effective `approval_floor`, and the audit record of a floor change names the stored values (`default` for no override) rather than the effective ones. On a hosted worker with no trusted device a floor change applies on its ticket alone, so it takes the standing the first pairing does: the owner's own ticket, or one whose `act_role` is owner or admin. An opt-down written while no device was trusted is cleared when the next first device is paired, and the clearing is recorded. Pairing a key under an approver id that already holds a different trusted key retires that key as a revocation would, so on a hosted worker it takes the ticket of the person that key is bound to, or an owner's or admin's; a key paired before keys named a person can be replaced only by an owner or admin. A held replacement applies only while the key it was approved to replace is still the one under that id.

Two hosted instances of one tenant currently serialize trust changes per instance, not in the database; hosted workers are capped at one instance until that write is transactional.

### Which gateway a device signature is for

One device key is trusted by every gateway its owner pairs it with, so a signature has to say which gateway it was made for, or a gateway that showed the device another gateway's held call could collect the signature and replay it there. Each gateway mints a random **approval audience** once (`aud_` and 32 hex characters, kept in `gateway_meta` as `approval_audience`) and serves it as `approval_audience` on every approval (`GET /v1/approvals`, `GET /v1/approvals/:id`), on the keyring listing (`GET /v1/approver-keys`) and in the answer to a pairing (`POST /v1/approver-keys/pair`, 200 and 202). The phone and the watch pin it per gateway at pairing, and the version 2 preimages bind it as their first field under their own domains (`permaura-relay/v2/approval-result`, `permaura-relay/v2/device-control`). The gateway refuses a version 2 signature whose audience is not its own. The desktop signs only for the gateway it supervises over loopback and binds whatever audience that gateway serves.

Version 1 signatures name no gateway, and the gateway refuses them. A device whose app has no pin for a gateway (one paired before the audience existed, or whose pin was never written) signs with no audience there, so it is refused with a message telling the approver to pair it with the gateway again. `PERMAURA_ACCEPT_V1_DEVICE_SIGNATURES=1` accepts version 1 again for approver apps that predate the audience, and the gateway logs a warning on every boot while it is set. Even then, once an approver has presented a valid version 2 signature to a gateway, that gateway refuses version 1 from it (the ids are kept in `gateway_meta` as `device_sig_v2_approvers`).

### What the approver was shown

`request_hash` binds a signature to the held call's full parameters, but a signature is only consent if the approver saw them. Every approval therefore carries the parameters rendered as rows of `path`, `state` and `value`, in sorted key order, with strings quoted and with invisible, direction-changing, combining, format and look-alike-space characters and Mathematical Alphanumeric letters spelled out, as are Cyrillic, Greek or Armenian letters mixed into a Latin word (`p\u{0430}ypal.com`). The approval's `capability`, `resource`, `message` and `action_description` are served escaped the same way, and the agent's stated reason is served apart as `intent` (escaped, cut at 280 characters), so a surface can label it as the agent's claim and set it against the parameters.

There are two renderings. `params_display`, on every approval read, is capped for cards: strings past 120 characters are cut with their full length shown, containers below four levels collapse to a count, rows past 32 are counted in `omitted`, and `complete` says whether any of that happened. `params_display_full`, on `GET /v1/approvals/:id` only, has no row, depth or length cap; above 256 KiB of rendered text (the gateway's default request body ceiling) it is served as `too_large` instead, and such a call can only be denied: to allow calls like it, change the policy rung for the action. For a capability with a pinned request shape (an imported one), only the parameters it forwards are rendered.

Rendering is redacted before anything is served. These are heuristics for the names and shapes listed here, not a guarantee that every secret is caught; an operator who knows a field is sensitive adds it to the connection's or policy's `redact_fields`, which the rendering honors.

- A value is shown as `set, N characters` when its name is in the call's redaction set (the gateway defaults plus the connection's, its manifest's and the holding policy's `redact_fields`, dotted paths such as `card.number` included) or matches the name rules: names containing secret, password, passwd, passphrase, passcode, credential, authorization, cookie, bearer, mnemonic, a recovery or backup phrase or code, or a seed phrase; names ending in `token` (a numeric `tokens` count stays visible); `api_key`, `private_key`, `access_key` and other qualified keys; `basic_auth`, `proxy_auth` and `auth_header`; session identifiers (`session_id`, `JSESSIONID`, `PHPSESSID`); MFA, OTP and OAuth codes (`mfa_code`, `verification_code`, and a bare `code` beside `grant_type`, `redirect_uri` or `code_verifier`); `pin`, `otp`, `cvv`, `cvc`, `ssn`, `pan`, `card_number` and `security_code`, and a `number`, `cvc` or `cvv` inside a `card` object; short and translated password names (`pass`, `pw`, `pwd`, `psw`, `creds`, `passwort`, `kennwort`, `contraseña`, `mot_de_passe`, `parola`, `heslo`, `clave`, `mdp`, `senha`, `пароль`, `密码` and others). A string `seed` is redacted and a numeric one is not. Identifiers, fingerprints, public keys, counts, null and booleans stay visible, and so do a bare `key` or `auth`. The bank account a payment goes to is shown in part, because it is what a person approving a payout has to check: a value under `iban` shows its country and check digits and its last four (`DE89[redacted]3000`), and one under a name containing `account_number` its last four (`[redacted]6789`). Only a value shaped like an account is shown that way; anything else under those names, a name the call's redaction set lists, a name/value pair and a mention inside a string stay redacted. The payee's name, BIC, routing number and sort code were never hidden.
- In a name/value list (`name`/`value`, `key`/`value`, `header_name`/`header_value`, `k`/`v`, or two-item arrays), the value beside a secret's name is redacted.
- A whole value shaped like a credential is redacted: a PEM block (OpenSSH keys included), `<scheme> <token>` authorizations (Bearer, Basic, Token, Digest, AWS4-HMAC-SHA256 and others), a JWT or JWE, a token with a known prefix (`sk_live_`, `ghp_`, `xoxb-`, `ya29.`, `hf_`, `SG.`, `AKIA` and others), a 40-character AWS secret key, a raw DER key (`MII…`) or an OpenSSH key body. A credential inside a longer string is replaced by `[redacted]` with the rest shown (state `masked`): those shapes anywhere in the string, URL passwords, secret query values (`key`, `sig`, `signature`, `access_token` and secret-named parameters), Slack, Discord, Teams, Zapier and IFTTT webhook URLs, `name=value`, `name: value`, `"name":"value"` and `--name value` assignments to a secret's name, SQL `PASSWORD '…'`, and `Password=` in connection strings.
- A control-plane mutation whose kind carries or points at sealed material shows only its `kind` and its identifiers; every other field is redacted, including any a later kind adds.
- The agent's stated reason is cut to 4 KiB, saying so, and masked the same way before it is stored on the hold or written to the audit chain.

Masking runs in time linear in the string's length, so an agent cannot stall the approval queue with a crafted value.

A device that approves computes a digest over the full rendering it put on screen together with the capability, resource, risk, description, message and intent (`approval_display_full_digest`, a length-prefixed layout under `permaura/approval-display-full/v1`) and binds it into the version 3 preimage (`permaura-relay/v3/approval-result`, the version 2 fields with the digest after `request_hash`). The gateway recomputes the full rendering from the held row and refuses an approve over any other rendering or of a call too large to render, so a broker cannot show the approver one call and have the device sign another, and padding can push a parameter off a card but never out of what is approved. A card may offer Approve only when its compact rendering is `complete`; otherwise the approver reviews the full rendering first. A denial is never refused for its rendering, because it runs nothing. A version 3 signature with an empty audience is held to the version 1 rules. Approver apps refuse to approve when the rendering is missing, unreadable, inconsistent with its own digest, too large, or different from the one they displayed.

Every device-signed approve has to bind the display. Apps that predate the rendering (phone builds before 46, desktop before 1.4.8) sign version 1 or 2, so they can no longer approve; a version 2 app with a pin can still deny. `PERMAURA_REQUIRE_DISPLAY_BOUND_APPROVALS=0` accepts an approve that does not bind the display again, with a warning logged on every boot while it is set; even then, once an approver has presented a valid version 3 signature, the gateway refuses an approve from it that does not bind the display (the ids are kept in `gateway_meta` as `device_sig_display_approvers`).

## Tamper-evident audit chain

Every policy decision and every execution appends an audit event: a denial, a hold, the `attempt` written before a call is sent, and the call's outcome. So do the control-plane changes the gateway applies through its hold check (policy, grant, agent, capability and connection changes and deletions, connector installs and removals, the broker pause and the agent-approval gate), changes to the approval floor and the approver keys, vault exports and imports, and the authority events: minting or revoking a session (over REST or the agent's own `permaura_revoke_session`), minting an enrolment code, and resetting the approvers.

Not everything is recorded. A call refused before it reaches policy leaves no event, by design, so that refusing a call costs less than serving one: a call refused while an execution hold is in force after a restore, while the deployment has paused agents (`PERMAURA_AGENTS_PAUSED`), while the gateway drains to stop, from a session over its denial budget, for a capability the gateway does not have, above the size ceiling, with a bearer that does not authenticate, or over a rate limit. The operator's own broker pause is a policy-time denial and is recorded. Creating a connection is not recorded, and neither is a credential written over loopback; one written from off the host with nothing to hold it is.

Three mechanisms make the log tamper-evident.

1. **Hash chaining.** Each event stores the hash of the previous event and its own hash covers both its content and that link, so altering or deleting an event inside the chain breaks every later link.
2. **ed25519 signatures.** Events are signed with a per-gateway key. Locally the key is an owner-only file beside the database, so anything that can write the database as the owner can read the key and sign a rewrite; on a hosted worker it is stored wrapped under the tenant's Cloud KMS key, and each cold start publishes a signed checkpoint of the chain head to the process log, which the holder of the database cannot rewrite. A store whose key is lost can be given a new one (`permaura audit rekey`): the first event under the new key names the old chain's head, verification reports that fork, and the events before it are from then on checked for their hashes and links but not their signatures.
3. **A pinned public key.** Both checks above use the key the store holds, so whoever can rewrite the store can re-sign a rewritten history under a key of their own and the chain still verifies. To catch that, every authenticated audit surface (`GET /health`, `GET /v1/broker`, `GET /v1/audit-events`, `GET /v1/audit/verify-full`) reports the chain's public key as `audit_key`: the base64 key and its full SHA-256 fingerprint. The permaura.com console records the key the first time it sees a gateway report it and shows a gateway that later reports a different one as a changed signing key rather than a verified chain. It is trust on first use: a key replaced before the console first saw the gateway is the one it pins, and a gateway reached only directly from the browser, never through permaura.com, is never pinned.

The gateway never edits an event in place, and events are exportable. They carry no credential the gateway holds and no request or response body: a call's event records its status, the shape of its result (a record or field count), the grant and policy behind it and the agent's stated reason after masking. That masking is the approval rendering's heuristics, so a secret an agent pastes into its reason under no recognizable name or shape is recorded as written. Two limits apply to the chain itself. Removing events from the end of the chain leaves a shorter chain that still verifies, and only a checkpoint of the head shows it: a hosted worker publishes one to Cloud Logging at each cold start, nothing compares the store against it automatically, and a self-run gateway publishes none. And the oldest events are moved to signed archive segments, each written create-only and read back, before they are pruned from the live store: a self-run gateway keeps them under `audit-archive` in its home unless `PERMAURA_AUDIT_ARCHIVE=0`, and a hosted worker publishes them to a bucket where one is configured. A segment in a bucket that grants create and no overwrite cannot be changed by the gateway; one in a self-run gateway's home can be rewritten by anything that can write the home, as the live store can.

## Redaction

Before a response returns to the agent, the value of every field whose name is on the call's redaction list is replaced with `[redacted]`. The gateway's defaults are:

```text
api_key  apikey  access_token  refresh_token  token  authorization  auth  cookie
set-cookie  password  secret  private_key  client_secret  session_token
card_number  pan  cvv  cvc  ssn  database_url
```

Both passes match field names, not values: a secret under a name that is not on the list, or inside a longer string, is not caught by them. A connection's, manifest's or policy's `redact_fields` adds names to the list, and nothing can remove a default. The name a call's own credential is sent under is added as well, in its hyphen and underscore spellings: an API key header or query parameter (an `xi-api-key` header also redacts `xi_api_key`), or a command's secret env var.

The credential a call injected is also removed by value, before the name pass. Every occurrence of it in the result (strings, object keys, and numbers when the credential is all digits), the upstream's response headers, the error text and the diagnostics row is replaced with `[redacted-credential]`: the value as stored or trimmed, its JSON-escaped form, its base64 in either alphabet (also inside a longer encoded blob, and as the `<key>:` an HTTP Basic header carries), the password half of a `user:pass` value, each line of a PEM key, and any percent-encoding of those. For an OAuth connection that covers the access token, a refreshed one, the refresh token and the client secret. A credential shorter than 8 bytes is not scrubbed by value, because it would match ordinary text; other secrets an upstream returns are still caught by name only.

## Approval gates

Actions above a policy's risk threshold pause until a human resolves them. An approval is single-use, bound to the exact action and parameters, logged and revocable. A held agent call does not expire: it waits until it is approved, denied or revoked. A held control-plane change lapses 24 hours after it was held, so a stale request (removing someone's device, say) cannot be confirmed days later, and a held vault export lapses sooner, as below. A call held at the `approve` rung can be resolved with the operator's session (the console or the CLI) or by a paired device; one held at `device_signed` needs a paired device's signature: a phone, an Apple Watch, or the Mac running the desktop app. A policy can require more than one person to sign (n-of-m): the quorum counts distinct people, so a phone and a watch paired to one person count once, and so do keys paired before devices named a person, between them. Revoking a device removes its signature from any approval still pending; once an approval is resolved, that resolution is the commit point for the human decision, and a later revocation does not undo it. What is re-checked at that point is the authority the call was made under and the world it acts on: the session that made it not revoked, not expired and still present, the capability still enabled and its connection present, the agent still approved, the policy unchanged, the grant unexpired and within budget, and the gateway not paused. Revoking a session therefore also stops the calls it has waiting: they stay in the queue, but approving one settles it `denied` with the reason `session_ended` and sends nothing upstream. Once a device is paired, loosening the gateway's own trust settings takes that device's signature, a recovery code or a recovery ticket, whatever the caller presents, and every vault export and destructive mutation is held for a device signature unless the floor has been explicitly lowered to `approve` (itself a loosening of that kind). Removing an agent that is still waiting to be approved is not destructive: it holds no access and no grant names it, so that removal applies at once wherever it comes from. Other control-plane writes over loopback apply without one, except a change that moves where a stored credential is sent (see Same-user boundary); over the broker they are held unless they only tighten or the floor has been lowered. A held vault export differs in two ways: once approved it can be collected only by the caller that requested it, with a single-use secret returned to that caller alone, and it lapses ten minutes after the request.

A held control-plane change or vault export records who asked for it: the member permaura.com names in the console's operator token, or the actor a step-up ticket names (a request made at the gateway's own host names nobody). A device paired to that person does not confirm it alone while a device paired to someone else is trusted, and a device paired to nobody in particular (one paired before devices named a person) confirms it only when no device paired to someone else is trusted. Where the requester's own devices are the only ones trusted, as on a gateway with a single owner, they confirm it as before, and a device paired to the gateway's owner confirms a change whoever asked for it. Above a quorum of one the requester's device may be one of the signers, because the quorum counts distinct people and so cannot complete without someone else. A change that moves where an SSH connection's stored credential is sent or how it is presented (its host, port, user, host key, or a switch to password sign-in) takes, from off the host, the standing a vault export does: the gateway's owner, or a member whose console token permaura.com signs as holding Export the vault (`vault_export`), or on a self-run gateway its own operator bearer. A role alone does not confer it, so an organization admin without Export the vault is refused. A hosted worker with no paired device refuses such a change outright. A vault import from off the host that would set the credential of a connection already here (an id a connection or capability names, with no stored value behind it) goes exactly as a credential written through `POST /v1/secrets` does: held by reference for a device signature while one is required, when the import answers 202 with the held approvals and writes the rest, and otherwise written. A credential a connection uses that is written from off the host with nothing to hold it (no device paired, or approvals opted down) is recorded in the audit chain with the same reason whichever of those routes wrote it. Installing or removing a connector manifest is a control-plane change too: from off the host it is held for a device while one is required and refused where nothing could hold it, and every install is recorded with the manifest's id, its provenance and the host it pins. A manifest Permaura did not sign may not take the id of a bundled preset or of a connector family the gateway builds itself, and a connection under the id of a family with a fixed host (GitHub, Braintree, Vercel, fal) must send its credential to that host. A held credential names the host it will be sent to.

A held change that lowers the number of people an action needs (an n-of-m rule edited down, its policy or grant removed or disabled) needs the people the rule did. The gateway also keeps a high-water mark for each connection and action a rule above one person has held, recorded before any policy or grant change applies, so taking the rule out of force in a step that only tightens (moving the action to deny, disabling its grant) does not let a later step put the action back below it at one signature: newly permitting the action, or permitting it for an agent below the mark, needs as many people as the mark. Marks apply to a connection and action across all agents. A rule requiring two people for one agent can therefore require two signatures when granting that action to another agent, even if the second agent has never been subject to that rule. This conservative behavior also applies when a separate deny rule currently masks the first agent's access. The mark is cleared only when a change signed by that many people moves the action. Lowering the approval floor, which switches every device hold off, needs the highest quorum in force or marked, capped at the number of people the trusted devices belong to, so a gateway with one owner and one device can always lower it.

With no trusted device there is nothing to hold for, so a self-run gateway refuses outright any request from off the host (a web page, the tunnel, another machine's CLI, or anything authenticated with a permaura.com token, which counts as off the host however it arrived because a configuration permaura.com's Cloudflare account pushes to the managed tunnel's connector, or private-network traffic it routes through it, reaches the gateway from its own machine until the gateway stops the connector, about a second later) that would reach a credential already here: a vault export, an import that would replace a connection or capability or attach new ones to an existing credential, a new connection whose credential slot already holds a secret, whether sealed locally or held by an external custodian such as Infisical, and an SSH edit that changes where a stored credential is sent or how it is presented. Loopback callers on the gateway's own machine, hosted workers and gateways with a paired device are unaffected and behave as described above, except that a hosted worker with no paired device refuses the SSH edit as well. A refused export or import is recorded in the audit log; a refused connection or SSH edit is answered with a 403 and leaves no audit entry. Every other edit still applies from the console, so until a device is paired, console code can configure the gateway and use its credentials through an agent it approves, without reading them.

## Same-user boundary

On a machine that runs the gateway and its agents as the same OS user, same-user is not a security boundary. Any process the owner runs can read `$PERMAURA_HOME/operator.token` and call the API directly, and on Windows and file-custody Linux it can read the vault key too. Ordinary policy and connection writes over loopback trust that operator, so a paired device bounds the damage rather than closing the boundary: vault export, destructive mutations, trust changes and any change that moves where a stored credential is sent or how it is presented (an SSH target or auth kind, an import that replaces a connection or attaches to a credential already here, a new connection that takes over an existing credential) wait for the device or are refused (see Approval gates), but an attacker holding only the operator bearer can still resolve any held call at the `approve` rung unless the floor is raised, and grant access. What turns the OS user into a boundary the kernel enforces is running the gateway under its own identity (`--service-user` on Linux) or keeping agents in a separate account or VM. Placing the agent in a container that mounts the owner's home does not.

## Account recovery is a trust choice

A gateway with remote access configured is an OAuth resource server for permaura.com, and that makes permaura.com's recovery ticket a valid third authority for the two trust-loosening controls above. It exists so the people who manage a gateway can get back in when its devices and codes are gone, and those people change over time: permaura.com mints one only for whoever is an owner or admin of the gateway's organization at that moment, after a fresh re-authentication, and the ticket names that person and their role. The gateway accepts its owner's own ticket, or one whose role is owner or admin, and refuses any other member's; the audit record names the actor and the role it rested on. The consequence is that an account-recoverable gateway trusts the account and ticket authority as part of its custody, including its word on who holds those roles: a compromised authorization server could assert the re-authentication, or the role, itself. That reaches the devices: a ticket naming the owner revokes a trusted device at once, the last one included, which switches the device holds off, and on a hosted worker, whose first device is paired on a ticket, the same authority can then pair a device of its own. Each step is recorded in the audit chain. A gateway without remote access has no such route and no such trust.

## Hosted mode

Each hosted tenant runs in its own Cloud Run service with its own runtime service account, its own store, its own vault key in Secret Manager and its own Cloud KMS key. KMS wraps the audit signing key and any secret explicitly enrolled to KMS custody; ordinary secrets are sealed under the vault key as above. Command capabilities are refused on a hosted worker.

The store is the same SQLite database every self-hosted install uses. It lives in the instance's own memory, which does not survive a restart, so a consistent copy of it is written to a Cloud Storage bucket belonging to that tenant alone before any request that changed state is acknowledged. The bucket is encrypted under the tenant's own KMS key, and its policy grants access to the tenant's runtime service account alone. Every acknowledged write makes a new version of the snapshot, and the versions it replaces are kept for up to thirty days, at most 100 of them, so on a busy tenant the oldest version that can still be restored may be only minutes old. The audit signing key is held KMS-wrapped inside the database rather than in a file beside it, so it travels with the snapshot and the chain continues across a restart instead of forking onto a new key.

The worker does not authenticate the snapshot. It opens whichever version of the database is live, with no signature or MAC of its own over it, so its integrity rests on who can write the bucket: the runtime service account, the project's owners, and anything allowed to act as that account. Write access to the bucket is control of the tenant, because the approver keys, sessions and grants are all in the snapshot.

The honest statement is the one Permaura has always made: a worker that performs the call can decrypt the secret at call time. The runtime identity is authorized to read the vault key, the database and the KMS key, so a compromise of that runtime reaches that tenant's secrets. Console and phone app traffic that carries a credential (adding a connection or a secret, or importing a vault bundle with its passphrase from the console) passes through permaura.com's broker on the way to the worker, over TLS, in a form the broker could read. Direct MCP traffic from an agent does not pass through the broker. Customers wanting stronger guarantees choose local execution or a tunnelled self-run gateway.

## Kill switches

Each control below acts on the running gateway when it answers, unless the row says otherwise. Pausing, disabling and revoking only tighten, so they apply at once from anywhere. Removing an approved agent or a grant is a destructive change, held for a device signature once a device is paired unless approvals have been opted down, so pause first when it has to stop now. Undoing a pause or a disable from off the host is a loosening, held the same way.

| To | Use |
|---|---|
| Stop every agent call at once | Pause the broker: `POST /v1/broker/pause` with `{"paused": true}`, the console's pause. Every agent call is then denied, and recorded, until it is lifted, and the setting survives a restart. |
| End one session and the calls it has waiting | `POST /v1/sessions/:id/revoke`, or the agent's own `permaura_revoke_session`. A held call from a revoked session that is approved later settles `denied` and sends nothing. |
| Cut one agent off | Pause the grants that name it. `DELETE /v1/agents/:id` removes the agent, its sessions and its grant memberships. |
| Withdraw a grant | `PUT /v1/grants/:id` with `"enabled": false` pauses it; `DELETE /v1/grants/:id` removes it. The Default grant can be paused but not deleted. |
| Stop one connection or capability | `PATCH /v1/connections/:id` with `{"disabled": true}`, or switch the capability off on its connection. |
| Rotate an affected secret | `POST /v1/secrets/:id/rotate` with the new value, after rotating it at the provider. |
| Remove remote access | `permaura remote disable` removes the tunnel and OAuth settings from the gateway's configuration, and reports whether the running gateway has stopped serving remotely or keeps serving until it restarts. Settings supplied through the environment, such as an installer's `gateway.env`, outrank the file and have to be removed there. |
| Stop the gateway | `permaura stop`, an authenticated `POST /v1/shutdown` over loopback. |

There is no single control that revokes every session or every grant; pausing the broker is the one that stops every agent at once.

## Supply-chain controls

The gateway release manifest is ed25519-signed and every installer path verifies it; the published macOS gateway is signed with a Developer ID; the desktop app is signed and notarized on macOS and its updates are signed. Connector manifests are signed under a root, intermediate and leaf chain, and release builds trust only the production root. The Windows installer is not yet Authenticode-signed and shows a SmartScreen warning; Linux packages are unsigned. Dependencies are audited in CI and the repositories are scanned for leaked secrets on every push.

## Summary of guarantees

- The model never receives a raw secret; there is no tool that returns one.
- Stored secrets are envelope-encrypted with per-secret AEAD keys wrapped under a key derived from a random vault key that lives outside the database, in the OS credential store where the platform and build allow it and in an owner-only file otherwise.
- Every policy decision and every execution, and the configuration and authority changes listed above, are recorded in a hash-chained, ed25519-signed audit log that carries no credential the gateway holds; the audit chain section says what is not recorded and what the chain does not detect.
- Responses are redacted before they reach the agent.
- The default answer is deny; permission is always explicit and scoped, and time-boxed when its grant sets an expiry. Once a device is paired the gateway will not loosen its own trust settings without that device or a recovery authority, and it holds vault exports and destructive changes for the device unless its floor has been explicitly lowered.
- Same-user isolation, hosted-worker isolation from Permaura, and hardware-backed key custody are not claimed.
